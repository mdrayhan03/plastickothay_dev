1What a cookie actually is

A cookie is just a key=value string the server asks the browser to store and replay. Two HTTP headers do all the work:

Server → browser:   Set-Cookie: refresh_token=abc; HttpOnly; Secure; SameSite=Lax; Path=/api/auth/; Max-Age=604800
Browser → server:   Cookie: refresh_token=abc          (attached automatically)

The browser keeps a cookie jar keyed by Domain + Path. On every outgoing request it asks: "do I hold cookies whose Domain / Path / Secure / SameSite rules match this request?" — and if so, attaches them. You never do this in JS; the browser does. The attributes decide when it will attach:

HttpOnlyJS (document.cookie) cannot read itXSS can't steal the token

SameSiteSent on cross-site requests? Strict/Lax/NoneThe crux of the bug (§5)

2Stateful vs stateless authentication

The real question after login: where does "who is this user" live — on the server, or inside the token itself?

Stateful (session-based) — Django's default

  1. You log in. The server writes a session record to a store (DB/Redis): session_id abc → {user:42, exp:…}.
  2. It sends Set-Cookie: sessionid=abc.
  3. Each later request carries Cookie: sessionid=abc; the server looks abc up to find user 42.

The cookie is an opaque pointer; the truth lives server-side.

  • ✓ Revocation is trivial — delete the row, session dies instantly.
  • ✓ Cookie is tiny.
  • ✗ Every request hits the store; scaling needs a shared store, not per-process memory.

Stateless (token / JWT)

  1. You log in. The server signs a token of claims {sub:42, exp:…} with a secret. Nothing is stored.
  2. The client sends the token on each request.
  3. The server verifies the signature and reads the claims — no lookup. The token is the proof.
  • ✓ No server state → any instance validates; scales trivially.
  • ✗ Revocation is hard — a signed token is valid until it expires. To kill it early you need a blocklist (a bit of state back). That's why this app uses simplejwt.token_blacklist — logout blacklists the refresh token.

3This app's hybrid model

It deliberately splits the two, taking the safer half of each:

TokenLifetimeStored whereSent howModel
Accessshort (minutes)in-memory JS variableAuthorization: Bearer …stateless — signature-verified
Refreshlong (7 days)httpOnly cookie, path /api/auth/browser auto-sendsstateless + blacklist on logout

Why this shape:

  • Access token in memory, not localStorage → XSS can't scrape it from storage, and it's short-lived so a leak is low-value.
  • Access token as a Bearer header, not a cookie → the browser doesn't auto-attach it, so API calls are CSRF-immune (a foreign page can't forge a custom header).
  • Refresh token in an httpOnly cookie → JS literally cannot read it. On boot the SPA calls /api/auth/refresh/, the browser attaches the cookie, and the server mints a fresh access token — that's how a page reload restores your session even though the in-memory access token was wiped.
◆ Key consequence
The entire "stay logged in across refresh" behaviour hinges on the browser being willing to send that refresh cookie on the boot request. Everything below is about when it will — and won't.

4Origin vs Site — the distinction everything rests on

  • Origin = scheme + host + port. https://app.example.org ≠ https://api.example.org ≠ http://app.example.org.
  • Site = the registrable domain (eTLD+1). app.example.org and api.example.org are the same site (example.org).

The two gatekeepers use different definitions:

  • CORS cares about origin — can JS read this cross-origin response?
  • SameSite cookies care about site — send this cookie on a cross-site request?
▲ Remember this
Two subdomains of one domain are cross-origin but same-site — CORS applies, yet SameSite cookies still flow. This single fact is the difference between a fragile deploy and a solid one.

5SameSite, precisely

ValueCookie IS sent on…NOT sent on…
Strictonly same-site requestseven a top-level link click from another site
Lax (default)same-site requests + top-level GET navigations from other sitescross-site subresource requests: XHR/fetch, images, iframes
Noneeverything, incl. cross-site XHR— but requires Secure (HTTPS)

Your refresh happens via axios — an XHR/fetch. If that call is cross-site, a Lax cookie is in the "not sent on cross-site subresource" bucket → the server sees no cookie → refresh fails → you're logged out. That is the bug in one sentence.

6CORS & cookies: two separate gates — pass both

For a cross-origin request carrying a cookie, two independent checks run:

  1. Will the browser SEND the cookie? → decided by SameSite (+ Secure/Domain/Path). Cross-site needs SameSite=None; Secure.
  2. Will the browser let JS READ the response? → decided by CORS. For a credentialed request the server must return:
    • Access-Control-Allow-Origin: https://your-frontend — the exact origin, never *, and
    • Access-Control-Allow-Credentials: true,
    and the client must set withCredentials: true.
✕ The classic double failure
Miss gate 1 → the request arrives unauthenticated. Miss gate 2 → JS can't read the reply (and Access-Control-Allow-Origin: * with credentials is a hard browser error). The original config failed both: SameSite=Lax (gate 1) and CORS_ALLOW_ALL_ORIGINS = * with credentials (gate 2).

Why the last row is fragile: a SameSite=None cookie on a different site is a third-party cookie. Safari (ITP), Brave, and "block third-party cookies" settings drop it — so some users log out no matter what your headers say. *.onrender.com is on the Public Suffix List, so each subdomain is its own site → you land squarely in the fragile row. The upgrade path is custom subdomains of one domain (app. + api.yourdomain) → that moves you to the middle row: first-party cookie, Lax works.

8The refresh-on-reload bug, end to end

  1. Login (works even cross-site): POST /api/auth/login/ returns the access token in the JSON body → app is authed in memory. A Set-Cookie for the refresh token comes back too.
  2. Reload: the in-memory access token is gone. On boot the SPA calls GET /api/auth/refresh/ to mint a new one.
  3. Cross-site + SameSite=Lax: the browser withholds the refresh cookie on that XHR → server sees no token → 401 → app falls back to anonymous → you must log in again.
◆ The fix (cross-origin)
Both gates, together: REFRESH_COOKIE_SAMESITE=None (→ Secure) so the cookie is sent, and CORS_ALLOWED_ORIGINS = <exact frontend origin> + CORS_ALLOW_CREDENTIALS=True so JS can read the reply, and CSRF_TRUSTED_ORIGINS for the Django-admin/session bits, and withCredentials:true on the client. Same-origin needs none of this — Lax just works.

9The security lens — why this design

  • XSS (malicious JS in your page) can read anything in localStorage and any non-HttpOnly cookie. → Access token lives in a closure variable (harder to reach, short-lived); refresh token in an HttpOnly cookie (unreadable by JS).
  • CSRF (another site forging a request with your cookies) only works on auto-sent credentials = cookies. → API auth uses a Bearer header (not auto-sent → CSRF-immune); the one cookie is path-scoped to /api/auth/ and SameSite-guarded, and refresh rotates + blacklists on use.
  • Net: cookies carry the refresh leg safely (httpOnly beats XSS); Bearer carries the API leg safely (no cookie → no CSRF). The hybrid takes the safer half of each.

10Decision cheat-sheet

  • Want it bulletproof? Serve the SPA from Django (same-origin). SameSite=Lax, zero CORS. Nothing here bites you.
  • Must split frontend/backend? Use subdomains of one custom domain (cross-origin, same-site) → keep Lax, add CORS. Robust.
  • Different sites (e.g. default *.onrender.com, or Vercel + Render → cross-site): you can make it work with SameSite=None; Secure + specific CORS, but accept that strict-privacy browsers may still drop the cookie.
PlasticKothay — refresh cookie is httpOnly · Secure · SameSite-configurable, scoped to /api/auth/. Access token: in-memory, Bearer. Same-origin by design (DEC-7); cross-origin needs the four-part fix in §8.
